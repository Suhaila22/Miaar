# تقرير تغطية الفجوات مقابل وثيقة متطلبات المنصة

هذا التقرير يوثّق ما تمت إضافته إلى تطبيق **مِعيار** استجابةً لوثيقة تدقيق المتطلبات التي رفعها المستخدم، بحسب الخيار الذي تم اختياره صراحةً: **"كل ما يمكن برمجته فقط"**. أي بند حقيقي في مستوى البنية التحتية أو التشغيل أو التعاقد (ولا يُعبَّر عنه ككود قابل للتشغيل داخل هذا التطبيق) تم توثيقه صراحة أدناه بدلاً من إسقاطه بصمت.

تُستخدم في هذا التقرير نفس لغة الحالة المستخدمة في وثيقة التدقيق الأصلية: **متحقق** / **متحقق جزئياً** / **غير متحقق (خارج نطاق البرمجة)**.

---

## أولاً: البنود المتحققة الآن (تمت برمجتها بالكامل في هذا الإصدار)

### 1. بوابة الأهلية قبل الترشيح — متحقق
جدول `eligibility_checks` وصفحة "فحص أهلية المشاركة": يسجّل نتيجة فحص الأهلية (نجاح/رسوب) لكل مستخدم مقابل كل جائزة، ويُربط لاحقاً بقيد صارم يمنع تقديم الترشيح دون تأكيد الأهلية أولاً.

### 2. سير عمل اعتماد الترشيحات متعدد المراحل — متحقق
جدول `nomination_approvals` وحقل `workflowStage` على جدول الترشيحات، بمراحل: `draft → quality_review → management_approval → submitted → result`. كل انتقال بين المراحل يُسجَّل بمن قام به والقرار والملاحظات (`workflow.advance` / `workflow.history`)، مع **قيدين مؤسسيين إلزاميين** قبل الوصول لمرحلة "مُقدَّم":
- تأكيد أهلية الجائزة (من البند 1).
- تصفية جميع المحكّمين المُسندين من تضارب المصالح (من البند 4).

### 3. تقويم الجائزة والمعالم الزمنية — متحقق
جدول `award_milestones` مع حالات (`upcoming`/`due_soon`/`completed`/`missed`) وربط بكل جائزة، متاح عبر tRPC و REST، وله واجهة إدارة في لوحة "الحوكمة والامتثال".

### 4. لجان التحكيم وتضارب المصالح — متحقق
- `judging_committees` + `committee_members` (رئيس/عضو/أمين سر) + `committee_meetings` (محاضر وقرارات الاجتماعات).
- `conflict_of_interest_declarations`: إقرار إلزامي من كل محكّم مُسند لكل ترشيح، ويُستخدم كبوابة فعلية (انظر البند 2) وليس مجرد تسجيل شكلي.

### 5. متابعة الإجراءات التصحيحية — متحقق
جدول `corrective_actions` يُنشأ تلقائياً من توصيات التحكيم الصادرة عن الذكاء الاصطناعي عند كل عملية تحكيم، ويُسند لمالك مسؤول مع أولوية وحالة ونسبة إنجاز وأدلة إغلاق (`owner/priority/status/progress/closure evidence`)، قابل للمتابعة من قِبل المالك أو المشرف.

### 6. البيانات المرجعية المُصدَّرة (فئات/قطاعات/مستويات/مؤشرات أداء) — متحقق
جدول `reference_data` بنمط ملكية وإصدار واعتماد مطابق للنمط المعتمد مسبقاً في المعايير الحاكمة (`draft → approved → retired` مع رقم إصدار ومالك ومعتمِد)، بدل استخدام قوائم ثابتة داخل الكود.

### 7. قاعدة معرفة لتأصيل مخرجات الذكاء الاصطناعي (RAG خفيف) — متحقق
جدول `knowledge_sources` مع مراجعة اعتماد (`pending/approved/rejected`) وربط بنوع البرنامج، ودالة `findGroundingSources` لاسترجاع المصادر ذات الصلة — بنية تأصيل أساسية قابلة للتوسعة لاحقاً بمحرك بحث دلالي حقيقي.

### 8. حوكمة مخرجات الذكاء الاصطناعي (تدقيق وقابلية للمراجعة) — متحقق
جدول `ai_output_logs`: كل مخرج ذكاء اصطناعي (تحكيم، ملخص ترشيح، نموذج توضيحي) يُسجَّل تلقائياً (`feature`, `outputText`, `confidence`, `sourceIds`) وقابل للمراجعة والتعليم (`unreviewed/approved/flagged`) من قِبل المشرف — دون أن يوقف تسجيل الفشل الميزة الأساسية (تسجيل بأفضل جهد، لا يكسر تدفق العمل).

### 9. سجل أحداث أمنية قابل للتصدير لأنظمة SIEM — متحقق
جدول `security_events` منظم (النوع، المستخدم الفاعل، عنوان IP، بيانات وصفية، الوقت) يُسجّل تلقائياً: نجاح/فشل تسجيل الدخول، التسجيل الجديد، محاولات الوصول دون تفويض (401) ومحاولات تجاوز الصلاحية (403). هذا **السجل نفسه** جاهز للاستيراد من أي منصة SIEM خارجية عبر REST API (`GET /api/v1/security/events`)؛ ربطه الفعلي بمنصة SIEM حقيقية (Splunk/QRadar/إلخ) بند تشغيلي وليس برمجياً (انظر القسم الثاني).

### 10. تصنيف بيانات الأدلة (Data Classification) وفحص البرمجيات الخبيثة — متحقق
- حقل `classification` (`public/internal/confidential/highly_confidential`) على كل دليل مرفوع، قابل للتحديد وقت الرفع.
- حقل `malwareScanStatus` مع خُطّاف فحص قابل للتوصيل (`scanBufferForMalware`) يستخدم ClamAV عند توفره على الخادم، ويُعلَّم الحالة "skipped" بشفافية عند عدم توفره بدل ادّعاء نظافة الملف كذباً.

### 11. تحصين أمني على مستوى الكود — متحقق
- رؤوس أمان HTTP قياسية عبر `helmet` (بما فيها CSP صارمة في وضع الإنتاج).
- تحديد معدل الطلبات (`express-rate-limit`) على كامل واجهة API، ومعدل أكثر صرامة على مساري تسجيل الدخول والتسجيل لمقاومة هجمات القوة الغاشمة.

### 12. طبقة REST/OpenAPI مُرقَّمة الإصدار — متحقق
واجهة `/api/v1` قراءة-في-الغالب فوق نفس طبقة الوصول للبيانات المستخدمة في tRPC، موثّقة عبر `openapi/v1.json` (متاحة أيضاً على `/api/v1/openapi.json`)، لدعم تكامل الأنظمة الخارجية (لوحات BI، أنظمة ERP/HR/DMS) التي تتوقع REST تقليدي بدل tRPC.

### 13. أدوات تشغيلية (CI/CD واستمرارية العمل) — متحقق
- خط أنابيب CI (`.github/workflows/ci.yml`): فحص الأنواع + الاختبارات + البناء + تدقيق التبعيات، عند كل دفعة/طلب دمج.
- سكربتات نسخ احتياطي واستعادة لقاعدة البيانات (`scripts/backup-db.sh`, `scripts/restore-db.sh`) قائمة على `mysqldump`، مع تأكيد صريح قبل أي استعادة.
- سكربت اختبار حمل أولي (`scripts/load-test.mjs`) باستخدام autocannon، جاهز للتشغيل ضد بيئة تشغيلية حقيقية.

### 14. لوحة إدارة وظيفية للوحدات الجديدة — متحقق
صفحة "الحوكمة والامتثال" (`/governance`) داخل التطبيق: تبويبات وظيفية (غير مصقولة بعمق تصميمياً) لكل وحدة من الوحدات أعلاه — التقويم، اللجان، الإجراءات التصحيحية، تضارب المصالح، البيانات المرجعية، قاعدة المعرفة، حوكمة الذكاء الاصطناعي، والسجل الأمني.

## ثانياً: بنود خارج نطاق البرمجة صراحةً (بنية تحتية/تشغيل/تعاقد)

هذه البنود **لا يمكن تحقيقها بكتابة كود** لأنها تتطلب أنظمة أو اعتمادات أو بيئات خارجية حقيقية غير متوفرة في بيئة التطوير الحالية. تم إبقاؤها **غير متحققة** بصراحة بدلاً من الادّعاء بتغطيتها:

| البند | لماذا هو خارج نطاق البرمجة |
|---|---|
| منصة SIEM فعلية (Splunk/QRadar/Microsoft Sentinel...) | يتطلب اشتراكاً/ترخيصاً وبنية تحتية أمنية مستقلة؛ التطبيق يوفر السجل المنظم الجاهز للتصدير فقط (البند 9 أعلاه) |
| جدار حماية تطبيقات الويب (WAF) وبوابة API مستقلة | مكوّن بنية تحتية للشبكة/الاستضافة، يُركَّب أمام التطبيق وليس داخله |
| اختبار اختراق مستقل (Penetration Testing) | يتطلب جهة تدقيق أمني مستقلة معتمدة، وليس عملية برمجية |
| بنية تعافي من الكوارث (DR) بمقاييس RTO/RPO فعلية | تتطلب مراكز بيانات/مناطق بديلة حقيقية وبنية تعافي مُختبرة فعلياً، لا يمكن محاكاتها بكود |
| تكامل الهوية الرقمية الحكومية (UAE Pass) | يتطلب اعتماد رسمي وبيانات اعتماد حقيقية من الجهة الحكومية المُصدرة |
| اتفاقيات مستوى الخدمة (SLA) وعقود الدعم | مستندات تعاقدية/قانونية، ليست كوداً |
| بيئات Dev/Test/UAT/Staging منفصلة فعلياً (فيزيائياً/سحابياً) | قرار بنية تحتية واستضافة يُتّخذ عند النشر الفعلي، وليس جزءاً من الشيفرة المصدرية |
| نتائج اختبار حمل فعلية على بيانات إنتاجية | التطبيق يوفر سكربت الاختبار (البند 13)، لكن الأرقام الفعلية تتطلب تشغيله ضد بيئة تشغيلية حقيقية بحجم بيانات واقعي |
| تكاملات فعلية مع أنظمة ERP/HR/DMS/BI حكومية | تتطلب بيانات اعتماد وواجهات برمجية حقيقية لأنظمة خارجية غير متوفرة في هذه البيئة؛ واجهة REST الجديدة (البند 12) تجعل هذا التكامل *ممكناً تقنياً* من جهة معيار، لكن لا يمكن تنفيذه فعلياً دون الطرف الآخر |

## ملاحظة ختامية

جميع البنود المتحققة أعلاه خضعت للتحقق التالي قبل التسليم:
- فحص الأنواع (`tsc --noEmit`) دون أخطاء.
- كامل مجموعة الاختبارات الآلية (82 اختباراً) ناجحة.
- بناء الإنتاج (Vite + esbuild) ناجح دون أخطاء.
- تطابق مخطط قاعدة البيانات مع ملفات الهجرة (`drizzle-kit generate` لا يُنتج تغييرات معلّقة).
- اختبار دخان (smoke test) لخادم مبني للإنتاج، يؤكد استجابة نقاط REST الجديدة بالتصنيفات الصحيحة (200 للعام، 401 لغير المصادَق، مع رسائل خطأ نظيفة).
